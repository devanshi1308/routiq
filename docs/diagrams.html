1. Activity Diagram — Sign in, route, payment and booking

End-to-end rider flow from sign-in to rating, with the decisions the app makes (driver accepts, rider cancels).

flowchart TD
  S(( )) --> A[Open app / splash]
  A --> OB{First launch on this device?}
  OB -- Yes --> OB2[Onboarding: three slides, Skip or Next, then Get started]
  OB -- No --> B
  OB2 --> B{Signed in?}
  B -- No --> RS{Toggle: Rider or Driver}
  RS -- Rider --> C[Choose: mobile number with country code, email, Google account or Apple ID]
  RS -- Driver --> C
  C --> D[Receive a 4-digit code that must match, resend after 15 s]
  D --> D2{Existing account?}
  C --> GA[Google: email, then password. Apple: Apple ID and password, then Share or Hide My Email]
  GA --> D2
  D2 -- No --> D3[Sign up: name and email, drivers also add vehicle and plate]
  D2 -- Yes --> RT
  D3 --> AL[First sign-in only: Allow your location screen]
  AL --> RT{Role}
  RT -- Driver --> DR[Driver screen: go online, accept requests as yourself]
  RT -- Rider --> E[Home: recent places and service tiles]
  B -- Yes --> E
  E --> F[Tap 'Where to?', a recent place, or a service tile such as Bike]
  F --> F2[A tile pre-selects its ride, e.g. Bike is listed first]
  F2 --> PP[Rank popular places: H3 ring search around the rider, trips per month, own trips boost, distance penalty]
  PP --> G[Plan your ride: Home, Work and saved chips, recent, popular and nearby places, or search]
  G --> H[Pick destination]
  H --> R1[Fetch routes: LRU cache and rate limiter first, then OSRM, else A* on place graph]
  R1 --> R2[Default = shortest route]
  R2 --> R3{Rider changes route?}
  R3 -- Yes --> R4[Pick Fastest / Alternative, fare updates with traffic]
  R3 -- No --> I
  R4 --> I[Choose ride: Auto, Go AC, Bike, Priority, Premier, XL]
  I --> J{Change payment?}
  J -- Yes --> P1[Open Pay with screen]
  P1 --> P2{Personal or Business?}
  P2 -- Business --> P3[Set up company and work email, switch on Use for my rides]
  P2 -- Personal --> P4[Toggle Uber balance, pick Cash or UPI, add voucher]
  P3 --> K
  P4 --> K
  J -- No --> K[Tap 'Choose Auto']
  K --> CP[Confirm pickup spot: map pin with address, Confirm pickup]
  CP --> FR[Backend only: log GPS jumps, two-device sign-ins and many cancellations, rider is never blocked]
  FR --> H1[Index rider into an H3 cell, search k-rings around it for vehicles - hexagons stay internal, not drawn]
  H1 --> SG[Backend: surge multiplier from demand and supply in the rider's H3 hexagon plus 6 neighbours, capped at 2x, applied silently to fares]
  SG --> FC[Backend: forecast demand 2 min ahead, nothing shown to the rider]
  FC --> BD[Badge Cheapest and Fastest options]
  BD --> PL[Routiq Pool: find look-alike trips with H3 start and end cells and similar time]
  PL --> QG[Keep only drivers with rating 4.6+ and acceptance 80%+]
  QG --> H2[Rank vehicles by distance, split into batches of 3]
  H2 --> L[Status = searching, send batch N]
  L --> SR[Rider sees 'N of M drivers didn't accept your ride', no driver names]
  SR --> SX{Rider adds extra fare or another ride?}
  SX -- Yes --> SY[Fare goes up by 10-40 rupees or the search restarts with the new ride type]
  SX -- No --> TR
  SY --> TR
  L --> TR[Driver app: Trip Radar shows the request with fare, rating, pickup and trip distance]
  TR --> M{Anyone in batch accepts?}
  M -- No --> M2{More batches?}
  M2 -- Yes --> L
  M2 -- No / rider cancels --> X[Status = cancelled, save as Cancelled ride]
  M -- Yes, driver taps Accept --> N[Show driver, vehicle, plate and PIN]
  N --> NP[Rider sees Pick-up in N min, PIN banner, driver card, Message, ride details]
  NP --> NC{Rider cancels?}
  NC -- Yes --> NR[Pick a reason, then Cancel ride or Find another driver for no fee]
  NR -- Find another driver --> L
  NR -- Yes, cancel --> X
  NC -- No --> N1[Driver sees turn-by-turn card and can open Google Maps to the pickup]
  N1 --> N2[Live ETA countdown, driver vehicle moves to pickup]
  N2 --> N3{Rider messages driver?}
  N3 -- Yes --> N4[Chat: rider and driver exchange messages]
  N3 -- No --> O
  N4 --> O
  N --> O{Rider cancels before pickup?}
  O -- Yes --> X
  O -- No --> P[Driver arrives, rider shares PIN]
  P --> P2{Correct PIN entered by driver?}
  P2 -- No --> P
  P2 -- Yes --> PS[Trip starts, Google Maps opens with directions to the drop-off]
  PS --> Q[Trip in progress: rider sees drop-off time, ride details, share, safety, message, support and tip options]
  Q --> RR[Arrive at destination]
  RR --> T[Show fare, collect payment]
  T --> BR{Business profile on?}
  BR -- Yes --> BR2[Email receipt to work address, add to travel report]
  BR -- No --> U
  BR2 --> U[Rate driver 1-5 stars]
  U --> V[Save to Activity history, becomes a recent place]
  V --> EV[Queue app events, flush a batch every 5 s to backend]
  X --> EV
  EV --> W(((End)))

3. State Chart Diagram — Trip lifecycle (with route and payment selection)

The same states used by TripStatus in store/index.ts and driven by timers in app/(root)/trip.tsx.

stateDiagram-v2
  [*] --> idle
  idle --> routing : destination picked
  routing --> idle : back
  routing --> confirming_pickup : rider taps Choose ride
  confirming_pickup --> dispatching : rider confirms pickup spot
  confirming_pickup --> routing : back
  dispatching --> searching : H3 ring search done, candidates batched
  searching --> driver_assigned : driver taps Accept on driver screen
  searching --> cancelled : rider cancels / no driver
  driver_assigned --> driver_arrived : driver taps I have arrived
  driver_assigned --> searching : rider taps Find another driver
  driver_assigned --> cancelled : rider or driver cancels
  driver_arrived --> in_progress : driver enters correct PIN and starts trip
  driver_arrived --> cancelled : rider no-show
  in_progress --> completed : driver taps End trip at destination
  completed --> [*] : fare paid and rated
  cancelled --> [*] : saved to Activity
  state routing {
    [*] --> shortest_default
    shortest_default --> other_route : rider changes route
    other_route --> shortest_default : rider picks shortest
    shortest_default --> paywith : rider opens Pay with
    other_route --> paywith : rider opens Pay with
    paywith --> shortest_default : method selected
  }
  state searching {
    [*] --> batch_1
    batch_1 --> batch_2 : driver declines or times out
    batch_2 --> batch_3 : driver declines or times out
    batch_1 --> [*] : accepted
    batch_2 --> [*] : accepted
    batch_3 --> [*] : accepted
  }
  state driver_assigned {
    [*] --> approaching
    approaching --> approaching : tick, update ETA and vehicle position
    approaching --> [*] : ETA reaches 0
    --
    [*] --> chat_idle
    chat_idle --> chat_open : rider opens chat
    chat_open --> chat_idle : rider goes back
  }
  state in_progress {
    [*] --> moving
    moving --> moving : update route progress
    moving --> [*]
  }

4. System Architecture — data flow (inspired by Uber's big data platform)

Source: Uber Engineering blogs on the big data platform and the rider app. Latency labels are Uber's published targets; this clone implements only the client queue and batching.

flowchart LR
  subgraph APP[Rider app - implemented]
    UI[Screens] --> Q[Event queue with standard metadata]
    Q -->|batch every 5 s| SEND[Batch sender]
  end
  SEND --> GW[API gateway]
  GW --> VAL{Registered schema?}
  VAL -- No --> DROP[Drop event]
  VAL -- Yes --> K[(Kafka changelog topics, Avro)]
  SVC[Backend services: trips, pricing, dispatch] --> K
  SVC --> WS[WebSocket gateway, live vehicle positions every 1 s]
  WS --> UI
  UI --> CACHE[LRU cache and token bucket] --> GW
  SCH[Schema service] -.-> VAL
  K -->|mini-batch every 10-15 min| ING[Ingestion, Hudi upserts]
  ING --> LAKE[(HDFS / Parquet data lake)]
  LAKE --> ETL[Incremental Spark ETL, under 30 min]
  ETL --> MOD[(Modeled tables)]
  MOD --> PRESTO[Presto / Hive / Spark queries]
  PRESTO --> DASH[Dashboards: funnels, heatmaps, surge, ML features]
  DASH --> SG2[Pricing and matching models]
  SG2 --> SVC
