1. UI Golden Rules (Shneiderman's 8) applied to the app

#Golden ruleWhere it appears in the app
1Strive for consistencySame black primary button, grey cards, Jakarta font, and the same back/close header on every screen. Vehicle illustrations look the same on Home, Services, ride list and history.
2Enable frequent users to use shortcutsRecent places on Home start a booking in one tap. Auto is pre-selected. "Later" lets power users schedule.
3Offer informative feedbackTrip screen shows each state (finding driver, on the way, arrived, on trip) with a progress bar and moving vehicle. The selected ride gets a black outline; the ETA shows on the map.
4Design dialogs to yield closureA booking ends with a "You've arrived" screen with fare, rating and Done. Cancelled trips are saved in Activity.
5Offer simple error handlingContinue/Verify buttons stay disabled until the phone number (10 digits) and OTP (4 digits) are valid. "No places found" message in search. Cancel is always available before the trip starts.
6Permit easy reversal of actionsBack arrow on every booking step, Cancel ride button, "Change number" on the OTP step, payment method can be switched before booking.
7Support internal locus of controlThe rider chooses destination, ride type, payment method and when to cancel. Nothing is booked until "Choose Auto" is pressed.
8Reduce short-term memory loadSkeleton loaders show layout while loading; the PIN stays on the trip screen; recent places and the driver's plate/vehicle stay visible; the fare is shown next to each ride type.

2. Software Requirements Specification (SRS)

Structure follows IEEE 830. Map each section to your Experiment 1–9 titles (table at the end).

1. Introduction

1.1 Purpose. Defines requirements for a mobile ride-hailing app (Routiq) for riders in India.
1.2 Scope. Riders sign in, choose a destination, compare ride types (Auto, Go AC, Bike, Priority, Premier, XL), book, track the trip, pay, rate, and view history, wallet, safety, inbox and help. Driver and admin apps are out of scope (driver actions are simulated).
1.3 Definitions. OTP – one-time password; PIN – 4-digit trip verification code; ETA – estimated time of arrival; SRS – Software Requirements Specification.
1.4 References. IEEE 830-1998; Uber India app (UI reference); Shneiderman's 8 Golden Rules.

2. Overall description

Product perspective. Standalone cross-platform app (React Native + Expo) with a mock backend; designed to later connect to a real API, maps and a payment gateway.
User classes. Rider (primary), Driver (simulated), Admin (future).
Operating environment. iOS 15+, Android 10+, modern browsers.
Constraints. Internet required for a production version; location permission; INR currency.
Assumptions. Drivers are always available within the city; fares are estimates.

3. Specific requirements

3.1 Functional requirements

IDRequirement
FR-1The system shall let a user sign in or sign up with a phone number and 4-digit OTP, an email, a Google account or an Apple ID, as a rider or a driver.
FR-2The system shall show recent places and service tiles (Auto, Trip, Bike, Rentals and others) on the Home screen; choosing a tile pre-selects that ride type.
FR-3The system shall let the user search places and select a destination; recent places shall be shown.
FR-4The system shall display each ride type with seats, ETA, arrival time and a fare computed from distance and time.
FR-5The user shall choose a payment method (Cash, UPI, Uber Cash).
FR-6The system shall assign a driver and show name, rating, vehicle, plate and a trip PIN.
FR-7The system shall show trip progress on the map and status text.
FR-8The user shall be able to cancel before the trip starts.
FR-9On completion the system shall show the fare and let the user rate the driver (1–5).
FR-10The system shall store completed and cancelled rides in Activity.
FR-11The system shall provide Wallet, Safety hub, Inbox, Help and Account screens.

3.2 Non-functional requirements

TypeRequirement
PerformanceScreens respond within 1 s; the fare list renders within 1 s of destination selection.
UsabilityFollows the 8 Golden Rules; a first-time user can book a ride in under 1 minute.
SecurityPhone/OTP authentication, trip PIN verification, no card data stored on the device.
ReliabilityTrip state is not lost on screen change; cancelled rides are recorded.
PortabilitySingle codebase for iOS, Android and web.
MaintainabilityModular screens, Zustand stores, mock data isolated in lib/mock.ts.

3.3 External interfaces

UI: touch screen, portrait. Hardware: GPS (future). Software: Maps API, SMS OTP provider, payment gateway (future). Communication: HTTPS.

3. Viva prep

  1. Which SDLC model did you use? Iterative/incremental: screens were built, previewed and improved in cycles.
  2. Functional vs non-functional requirement? What the system does (book a ride) vs how well (responds in 1 s).
  3. Why an activity diagram? It shows the workflow and decisions (driver accepts? rider cancels?).
  4. Why a state chart? A trip has a lifecycle: searching → assigned → arrived → in progress → completed/cancelled.
  5. Class diagram relations? User 1–* Trip, Trip *–1 RideType, Trip *–0..1 Driver, Driver 1–1 Vehicle.
  6. Name the 8 golden rules. Consistency, shortcuts, feedback, closure, error handling, easy reversal, locus of control, short-term memory.
  7. How is fare computed? base + perKm × distance + perMin × time (see fareFor in lib/mock.ts).
  8. What is mocked? Auth, drivers, map and payments. A real API can replace lib/mock.ts and the stores.
  9. Tech stack? React Native, Expo Router, Zustand, react-native-svg.
